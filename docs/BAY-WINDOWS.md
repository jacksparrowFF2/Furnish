# 飘窗整体与旧项目升级

2026-10-20。窗体和台体通过共同 `bayId` 组成一个飘窗；台面继续复用区域多边形和原有材料记录，不增加一份重叠的台面几何或家具对象。

## 数据与职责

- `src/core/bay-window-core.js` 共用整体、部件、外包范围、窗覆盖应用、台体高度同步和编辑锁定。二维选择、三维选择、属性、快捷栏消费同一关系；实时画布和独立项目派生均调用 `applyWindows()`，不各自解释窗高度与窗扇覆盖。
- 自定义生成飘窗的唯一几何来源仍为 `architecture.draft.openings[].bay`，单位 mm；保留 `depth/height/head/type`。`height` 为台面完成面高度，窗体下沿与其齐平。派生平台高度在现有渲染边界使用 m。
- 内置户型及其编辑副本保留实测／预设的原窗框、独立墙段和台面轮廓，窗与台面共用 `bayId`。内置示例调整高度沿现有 `open.w`；建筑编辑副本直接更新整组关联洞口及台体高度，面板和户型编辑器读取同一建筑高度，逐窗 `panels/stackSide` 保留。共同关系不要求将其强行改造成另一种外凸几何。
- 名称、台面饰材沿 `rooms[platform.id]` 保存，仍经 `mutate()`、撤销重做、自动保存及命名方案。结构锁定不禁止改饰材；台面所在物体图层锁定时禁止改饰材和几何。无新增家具字段。

## 选择与编辑

### 高度约定（2026-10-20 用户确认）

台面完成面与窗体下沿始终齐平，共用一个高度参数。内置和自定义飘窗均遵循此约定，不提供独立的窗体下沿高度、解除齐平开关或下沿偏移设置。

窗高 = 窗顶高 − 台面高度。修改台面高度时，窗体下沿同步移动，保持窗高并更新窗顶高；修改窗高或窗顶高时，另一项按该关系联动。此约定作为已确认的产品规则维护，独立下沿设置不列入后续计划。

### 部件选择与尺寸编辑

点击二维台面或窗面、三维裸露台面或玻璃／窗框，均打开同一飘窗面板；保留当前部件身份。面板提供整体尺寸、逐窗形式、台面名称／材料，并显示台面面积及不计入套内使用面积的说明。快捷栏提供窗体／台面切换；台面不再显示通用房间用途、地面铺砖、房间墙面工程量及房间内家具操作。

三维框选从当前可见的实际平台和窗体网格计算，不含隐藏层网格；图层清单仍保留原 `floor:<roomId>` 键，因此已有分层、显隐和锁定不迁移。清单将该项标为“飘窗 · 台面饰材”，不再生成虚构的台面天花条目。二维显示台面、窗面及整体范围。

窗高仍等于窗顶高减台面高，修改台面高保持窗高。正面窗飘窗保留原墙体，台面向室内量取进深并按原墙段裁切；三面外凸飘窗仍沿原外墙外皮向外量取进深。宽度和裁切遵循既有几何，不把台面实际宽度当作洞口宽度。

## 升级与保存

旧字段转换只在 `floorplan-core.upgrade()` 中实现：

1. 将旧洞口 `bayGroup` 转为 `bayId` 并删除旧字段；两者冲突时拒绝，不猜测关联。
2. 为与这些洞口明确关联的旧 `roomLayout` 台面补入相同 `bayId`。
3. 旧 `bay` 缺失类型时明确物化原先的 `three-sided` 默认值。

构建、工作恢复、导入和导出均调用该入口；当前方案、命名方案、结构基线、原始修订和户型登记一并升级。修改建筑洞口和结构锁定比较也使用归一化结果。没有修改原始数值、平面坐标、家具、材料或门窗方向。升级幂等，旧字段不在运行中的选择、编辑和渲染链路中继续传播。

包含这些建筑飘窗记录的项目／工作区使用外层版本 16，独立 `huxing-design-v16` 缓存，仍可读取旧版本。纯内置户型使用原有数据字段，不为界面变化强制补写建筑结构。仅有旧缓存时按原仲裁规则选择；新的 v16 缓存存在后优先使用它。

仓库服务读取时返回规范化工作区，但文件修订指纹仍按磁盘原工作区计算，使下一次保存能够真正写回升级结果。首次由旧版本写为 v16 时，先将旧完整工作区保存到 `.local/furnish-recovery`，再沿原锁文件／冲突校验／临时文件原子替换；重复保存不重复备份。

当前仓库 `projects/workspace.furnish.json` 已按此链路升级：9 套工作方案、1 份命名方案，数据差异仅 `workspace.v:15→16` 与外层版本。备份及实测记录见 [验收记录](validation/bay-assemblies-20261020.json)。其他历史导出文件保留原件，在读取／再次导出时升级，不遍历改写历史文件。

## 2026-10-20：升级后复查与当前项目验收

复查清理了三个界面各自复制的高度输入联动，统一为 `property-panel.js` 中的 `linkWindowHeightInputs()`；它保留原预览回调顺序，供普通窗、飘窗及户型编辑器复用。主画布和独立有效方案的窗覆盖解释也合并到 `applyWindows()`；生成式飘窗始终以建筑 `bay.height/head` 为垂直几何来源，逐窗形式覆盖不能拆分窗体下沿和台面高度。

修复“先改窗扇形式，再改台高／进深会重置窗扇”的缺陷。预览与确认通过同一个 `project-core.remapOpenings()` 规则更新几何高度，保留逐窗形式和叠合方向；普通窗与正面窗飘窗互转时保留正面窗设置。户型编辑器同样根据建筑高度变化更新覆盖。内置编辑副本的整组高度由 `floorplan-core.editOpening()` 同步到各窗面及台体，避免继续积累只在面板生效的高度覆盖。

同时移除了空的选择分支和三维定位中的重复飘窗分组计算。三面外凸与已有凹口仍保留各自的几何构造，旧 `bayGroup` 仍只在唯一迁移入口识别；这些职责不合并为另一套保存机制。

当前项目 `custom_mv37igji` 的两处正面窗飘窗原值为：台高均 647 mm，进深分别为 718／712 mm，窗顶分别为 2304／2295 mm。已在隔离快照中验证两处的二维显示、部件选择、窗扇设置、尺寸预览／取消、撤销重做、材料／名称、刷新、真实导出再导入，以及三维实际网格对齐、玻璃／框体点击和三维开启时直接改高后的重建。项目中已有的飘窗垫／窗帘会遮住台面和玻璃，因此同时检查正常家具视图与临时隐藏家具的观察视图。源项目文件 SHA-256 与快照一致，未写入测试编辑。

20 项相关 Node 套件、当前项目与通用飘窗的 HTTP／断网 `file://` 专项，以及既有正面窗编辑流程通过；桌面和 390 px 截图已目视检查。未运行全量检查、无关历史预览或实体触屏验收。记录与截图见 [本轮复查](validation/bay-review-20261020.json)。
